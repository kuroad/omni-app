Membedah nomor empat, yaitu **Skema Infrastruktur (Deployment)**, adalah tahap eksekusi di mana semua kode yang telah ditulis diangkat ke server nyata. Karena Anda menyebutkan akan menggunakan **Nginx** dan domain akan menyusul, kita akan merancang arsitektur ini berjalan di atas IP Publik (VPS) menggunakan *containerization* agar rapi, aman, dan mudah di-*scale* nantinya.

Pendekatan terbaik untuk tumpukan teknologi (Next.js, Node.js, PostgreSQL, Redis) adalah menggunakan **Docker Compose**. Dengan ini, Nginx akan bertindak sebagai "Pintu Gerbang Utama" (*Reverse Proxy*).

Berikut adalah rincian mendalam skema infrastruktur untuk omni-ensiklopedia HSR Anda:

### 1. Topologi Jaringan Container (Docker Network)

Alih-alih menginstal setiap aplikasi langsung di OS server yang rawan konflik versi, kita mengisolasi semuanya ke dalam *container*.

* **Jaringan Tertutup (Internal Network):** Buat jaringan Docker internal (misal: `hsr_network`). Frontend, Backend, Redis, dan PostgreSQL hanya akan berkomunikasi di dalam jaringan ini.
* **Isolasi Port:** Jangan buka *port* database (5432) atau Redis (6379) ke publik! Ini sangat berbahaya. Biarkan mereka hanya bisa diakses oleh *container* Backend.
* **Satu-satunya Pintu Keluar-Masuk:** Hanya *container* **Nginx** yang diizinkan membuka *port* 80 (HTTP) ke internet (IP Publik Anda).

### 2. Strategi Routing Nginx (Tanpa Domain Sementara)

Karena domain belum ada, pengguna akan mengakses aplikasi melalui IP Publik VPS Anda (misal: `[http://198.51.100.25](http://198.51.100.25)`). Konfigurasi Nginx (`nginx.conf`) akan membagi lalu lintas berdasarkan *path* URL:

* **Blok `/api/` (Jalur Backend):**
Semua *request* yang berawalan `/api/` (misal: mencari profil pemain) akan ditangkap oleh Nginx dan diteruskan (*proxy_pass*) ke *container* Backend (Node.js). Nginx juga akan meneruskan IP asli pengguna agar Backend bisa mencatat siapa yang melakukan *request*.
* **Blok `/` (Jalur Frontend):**
Semua *request* selain `/api/` akan diteruskan ke *container* Frontend (Next.js) untuk memuat halaman web HTML, CSS, dan JavaScript.
* **Blok `/assets/` (Jalur Statis - Opsional tapi Disarankan):**
Untuk gambar *Splash Art* berukuran besar yang diunduh dari raw data HSR, Nginx sangat efisien dalam menyajikan *file* statis. Daripada Next.js atau Node.js yang melayani gambar, biarkan Nginx membaca langsung dari *folder/volume* lokal. Ini menghemat RAM server secara drastis.

### 3. Keamanan Tingkat Nginx (First Line of Defense)

Sebelum *request* UID mencapai Backend (dan mengurangi jatah *rate limit* API Mihomo Anda), Nginx bisa memfilter *request* nakal:

* **Rate Limiting Nginx:** Tambahkan konfigurasi `limit_req` di Nginx. Misalnya, batasi 1 IP maksimal hanya boleh melakukan 5 *request* per detik. Jika lebih, Nginx akan langsung memblokir dengan status `503 Service Unavailable` tanpa perlu membangunkan Node.js.
* **Gzip / Brotli Compression:** Aktifkan kompresi gzip di Nginx. JSON dari Mihomo dan bundel JavaScript dari Next.js akan dikompres hingga 70% lebih kecil sebelum dikirim ke *browser* pengguna, membuat web terasa jauh lebih cepat.

### 4. Manajemen Penyimpanan (Persistence & Volume)

*Container* bersifat sementara (*ephemeral*). Jika server *restart*, data di dalam *container* akan hilang. Oleh karena itu, kita membutuhkan **Docker Volumes**.

* **Volume PostgreSQL:** Mapping *folder* `/var/lib/postgresql/data` di dalam *container* ke *folder* fisik di VPS Anda (misal: `./data/db`). Jika *container* database hancur, data lore, karakter, dan *relic* HSR Anda tetap aman di *hardisk* server.
* **Volume Redis (Opsional):** Redis bisa diatur agar menyimpan *cache* ke *disk* (AOF/RDB) atau dibiarkan murni di RAM. Untuk *cache* profil pemain yang umurnya hanya 10 menit, dibiarkan hilang saat *restart* tidak masalah.

### 5. Otomatisasi Pembaruan (CI/CD Pipeline)

Bayangkan ada *patch* baru di HSR (misal versi 3.0) dan Anda memperbarui kode UI Next.js di GitHub. Anda tidak perlu masuk ke server VPS secara manual untuk melakukan *pull* dan *build*.

* Siapkan **GitHub Actions**. Setiap kali Anda melakukan *push* ke *branch* `main`, GitHub akan otomatis masuk (SSH) ke VPS Anda, menarik kode terbaru, dan menjalankan perintah `docker-compose up -d --build`.
* Aplikasi ensiklopedia Anda akan diperbarui tanpa *downtime* yang signifikan.

### Langkah Eksekusi (Urutan Deployment)

1. **Persiapan Server VPS:**
Masuk (SSH) ke VPS Ubuntu/Debian Anda. Lakukan update OS dasar, lalu instal Docker dan Docker Compose. Jangan instal Nginx langsung di OS, kita akan menggunakan *image* Nginx dari Docker.


2. **Pembuatan Berkas Konfigurasi:**
Buat satu direktori khusus (misal: `/opt/hsr-encyclopedia`). Di dalamnya, buat berkas `docker-compose.yml` yang mendefinisikan 5 *services* (frontend, backend, db, redis, nginx). Buat juga folder `nginx/` untuk menaruh berkas `nginx.conf`.


3. **Konfigurasi Nginx (IP Mode):**
Tulis konfigurasi Nginx untuk mendengarkan port 80 pada atribut `server_name _ ;` (tangkap semua IP). Arahkan `location /api/` ke service backend, dan `location /` ke service frontend.


4. **Jalankan Aplikasi (Spin Up):**
Jalankan perintah `docker-compose up -d`. Docker akan menarik *image* Node, Postgres, Redis, dan Nginx, lalu menjalankan semuanya di latar belakang. Ketikkan IP Publik server Anda di *browser* untuk melihat antarmuka webnya.


5. **Persiapan Domain (Fase Selanjutnya):**
Ketika domain sudah dibeli, Anda hanya perlu mengubah `server_name` di konfigurasi Nginx menjadi domain Anda (misal: `hsr-wiki.com`), lalu jalankan Certbot (Let's Encrypt) untuk mendapatkan gembok hijau HTTPS (SSL).
