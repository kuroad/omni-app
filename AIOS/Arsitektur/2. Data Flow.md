Membedah nomor dua, yaitu **Arsitektur Aliran Data (Data Flow)**, adalah bagian paling krusial untuk mencegah server kehabisan *resource* atau IP diblokir oleh pihak ketiga akibat *rate-limit*.

Dalam membangun omni-ensiklopedia Honkai: Star Rail, aliran data wajib dipisah menjadi dua jalur independen: **Jalur Dinamis** (untuk UID pemain) dan **Jalur Statis** (untuk database ensiklopedia). Keduanya nanti akan digabungkan di level Frontend untuk menghasilkan antarmuka yang utuh.

Berikut rincian aliran datanya:

### 1. Alur Data Dinamis (Sistem Pencarian Showcase UID)

Alur ini menangani data yang terus berubah saat pemain memperbarui profil atau relik mereka di dalam game. Sumber utamanya adalah API Mihomo.

* **Langkah 1: Permintaan Klien (Client Request)**
Pengguna memasukkan UID (misal: `800123456`) di aplikasi web. Next.js (Frontend) tidak langsung memanggil API Mihomo, melainkan mengirim *request* ke *internal endpoint* di Backend (misal: `GET /api/showcase/800123456`).
* **Langkah 2: Pemeriksaan Cache (Redis Intercept)**
Backend (Node.js/Fastify) menerima *request* dan langsung mengecek Redis menggunakan *key* spesifik, contohnya `hsr:uid:800123456`.
* **Skenario Hit:** Jika data ditemukan (artinya ada yang pernah mencari UID tersebut dalam 10 menit terakhir), Backend langsung mengirimkan data dari memori Redis kembali ke Frontend. Proses ini biasanya hanya memakan waktu 5–20 milidetik.
* **Skenario Miss:** Jika data tidak ada atau sudah kedaluwarsa (*expired*), lanjut ke Langkah 3.


* **Langkah 3: Pengambilan Pihak Ketiga (Mihomo API Fetch)**
Backend melakukan HTTP GET ke API Mihomo (contoh: `[https://api.mihomo.me/sr_info_parsed/800123456?lang=id](https://api.mihomo.me/sr_info_parsed/800123456?lang=id)`).
* **Langkah 4: Transformasi & Sanitasi Data**
Respons dari Mihomo sering kali memuat data mentah yang sangat panjang dan berlebihan. Backend akan memangkas struktur JSON ini, hanya menyisakan data yang benar-benar dipakai oleh UI (misal: menghapus string ID yang tidak perlu, memformat angka desimal stat).
* **Langkah 5: Penyimpanan Memori (Cache Set)**
Backend menyimpan JSON yang sudah bersih ke dalam Redis dan menetapkan TTL (*Time-To-Live*) selama 10 menit.
* **Langkah 6: Respons Klien**
Data dikirim ke Frontend. TanStack Query di Next.js akan memproses *state*-nya, mematikan efek *loading*, dan Framer Motion akan menganimasikan kartu karakter (masuk dari bawah/samping layar).

### 2. Alur Data Statis (Sistem Ensiklopedia Lore, Relic & Skill)

API Mihomo hanya memberikan data dari 4 karakter yang dipajang di profil (*showcase*). Untuk membuat fitur "Ensiklopedia" yang berisi *semua* karakter, senjata (Light Cone), dan relik, aplikasi harus memiliki basis data sendiri yang bersumber dari repositori *raw data* HSR.

* **Langkah 1: Pekerja Otomatis (Cron Job/Worker)**
Sebuah *script* di Backend dijadwalkan berjalan setiap 24 jam (atau setiap ada *patch* baru). *Script* ini bertugas menarik data mentah (JSON) dari repositori GitHub penyedia raw data HSR (seperti Mar-7th atau Dimbreath).
* **Langkah 2: Ekstraksi & Normalisasi (ETL Process)**
Data mentah tersebut diekstrak dan dipecah untuk dimasukkan ke tabel-tabel relasional di dalam PostgreSQL.
* Tabel `characters` (ID, Nama, Elemen, Path, Base Stats)
* Tabel `skills` (ID, Tipe Serangan, Multiplier Damage)
* Tabel `relic_sets` (ID, Efek 2-piece, Efek 4-piece)


* **Langkah 3: Sinkronisasi Aset Visual**
Bersamaan dengan pembaruan *database*, *worker* juga mengunduh *asset* gambar baru (*splash art*, ikon *skill*) dan menyimpannya di *folder* lokal. Nantinya, gambar ini di-*serve* langsung secara statis oleh Nginx agar pemuatan gambar sangat cepat dan tidak membebani *bandwidth* pihak ketiga.
* **Langkah 4: Frontend Fetching (ISR/SSR)**
Saat pengguna membuka halaman Ensiklopedia (misal: daftar semua karakter), Next.js akan menarik data langsung dari PostgreSQL melalui Prisma/Drizzle ORM. Karena data ini statis, Next.js bisa mem-*build* halamannya secara statis menggunakan ISR (*Incremental Static Regeneration*), membuat waktu muat halaman nyaris instan.

### 3. Persimpangan Data (Menyatukan Statis & Dinamis di UI)

Keajaiban arsitektur ini terjadi di Frontend saat menampilkan profil UID pengguna.

Ketika API Mihomo mengembalikan data *showcase* pemain, data tersebut sering kali hanya berisi ID (*Character ID*, *Light Cone ID*) dan stat perhitungan akhir. Untuk membuatnya menjadi antarmuka yang estetik dan informatif:

1. Frontend mengambil data dinamis (status Crit, Atk, Relic roll) dari alur Dinamis.
2. Frontend secara simultan mengambil deskripsi *lore*, ikon elemen, dan detail efek *Light Cone* dari PostgreSQL berdasarkan ID yang diterima.
3. Kedua data digabung dalam satu komponen visual (misal: `CharacterCard.tsx`), menampilkan grafis yang lengkap mulai dari angka hasil *grinding* pemain hingga teks deskripsi bawaan game.

Pemrosesan terpisah seperti ini sangat ramah sumber daya. *Container* Node.js hanya fokus pada API dan Redis, sementara kueri kompleks untuk ensiklopedia ditangani sepenuhnya oleh PostgreSQL. Nginx tinggal duduk manis di depan mendistribusikan jalur *request* tersebut sesuai rutenya.
