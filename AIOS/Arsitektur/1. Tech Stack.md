Membedah tumpukan teknologi (Tech Stack) secara rinci sangat penting agar aplikasi tidak hanya estetik, tetapi juga tangguh menangani *rate limit* dari API Mihomo. Karena *deployment* akan menggunakan Nginx sebagai *reverse proxy*, arsitektur ini disusun agar optimal berjalan di lingkungan VPS atau *home server* (berbasis Linux/Docker).

Berikut adalah rincian mendalam untuk Tumpukan Teknologi aplikasi web omni-ensiklopedia HSR:

### 1. Lapisan Frontend (Client-Side & UI)

Fokus di lapisan ini adalah kecepatan muat, SEO (agar pemain bisa mencari build karakter di Google), dan interaktivitas yang mulus menyerupai antarmuka game aslinya.

* **Framework:** **Next.js (App Router) dengan TypeScript**
* **Kenapa:** Mendukung *Server-Side Rendering* (SSR) yang krusial untuk SEO ensiklopedia (misal: halaman profil karakter atau relik). TypeScript memastikan struktur data dari API Mihomo yang sangat kompleks (banyak *nested array/object*) tertangani tanpa *runtime error*.


* **Data Fetching & State:** **TanStack Query (React Query)**
* **Kenapa:** Sangat powerful untuk menangani data dinamis dari *showcase* UID. Mendukung fitur *stale-while-revalidate*, sehingga saat pengguna merefresh halaman UID, UI tidak akan *blank*, melainkan menampilkan data lama sambil mengambil data baru di latar belakang.


* **Styling Engine:** **Tailwind CSS + Shadcn UI**
* **Kenapa:** Antarmuka HSR banyak menggunakan efek *glassmorphism* (kaca transparan) dan gradien. Tailwind sangat efisien untuk meracik utilitas seperti `backdrop-blur-md bg-white/10` untuk meniru UI in-game. Shadcn digunakan untuk komponen dasar (modal, dropdown, tabs) tanpa membawa *file* CSS raksasa bawaan.


* **Animasi:** **Framer Motion**
* **Kenapa:** Digunakan untuk *micro-interactions* seperti efek *tilt* 3D saat *mouse* diarahkan ke gambar *Light Cone*, atau transisi antar halaman (misalnya dari halaman daftar karakter ke detail karakter) agar terasa mulus tanpa *loading screen* yang kasar.



### 2. Lapisan Backend (BFF - Backend for Frontend)

API Mihomo membatasi jumlah *request*. Jika Frontend menembak langsung ke Mihomo, IP *client* atau server bisa terkena blokir sementara. Backend ini bertugas sebagai perantara pelindung.

* **Runtime & Framework:** **Node.js dengan Fastify (atau HonoJS)**
* **Kenapa:** Fastify/Hono jauh lebih cepat dari Express.js dalam memproses *request* berulang. Lapisan ini tidak melakukan komputasi berat, hanya melakukan validasi UID, mengecek *cache*, dan merutekan ulang JSON dari Mihomo ke Frontend.


* **Mekanisme Rate Limiting Internal:**
* Diimplementasikan di level Backend untuk mencegah pengguna melakukan spam klik tombol "Refresh UID" yang bisa menghabiskan kuota *request* ke Mihomo.



### 3. Lapisan Manajemen Data (Database & Caching)

Data statis (lore karakter, deskripsi relik) dan data dinamis (status relik pengguna) harus dipisah.

* **In-Memory Cache:** **Redis**
* **Peran Krusial:** Saat pengguna A mencari UID `800123456`, Backend mengambil dari Mihomo, membalas ke pengguna A, dan menyimpannya di Redis dengan *Time-To-Live* (TTL) 10 menit. Jika 2 menit kemudian pengguna B mencari UID yang sama, Backend langsung mengambil dari Redis (hitungan milidetik) tanpa menyentuh API Mihomo sama sekali.


* **Relational Database:** **PostgreSQL**
* **Peran:** Menyimpan sinkronisasi data statis dari *repository* raw data HSR (seperti elemen, *path*, material ascension, formula *damage*). Relasi antar tabel di PostgreSQL sangat cocok untuk struktur HSR (Karakter *has_many* Relik, Relik *belongs_to* Set, dsb).



### 4. Lapisan Infrastruktur & Deployment (Nginx Setup)

Karena Nginx akan digunakan sebagai garda terdepan sebelum *request* masuk ke aplikasi, struktur *deployment*-nya idealnya dibungkus menggunakan **Docker** dan `docker-compose`.

Arsitektur penempatan Nginx nantinya akan bekerja seperti ini:

1. **Nginx** mendengarkan *port* 80/443 (saat domain dan SSL sudah siap).
2. Nginx mengatur kompresi **Gzip/Brotli** (krusial karena respons JSON Mihomo API ukurannya bisa sangat besar).
3. **Routing Block Nginx:**
* Jika *request* masuk ke `[domainanda.com/api/](https://domainanda.com/api/)*`, Nginx meneruskannya (*proxy_pass*) ke *container* Node.js (Backend).
* Jika *request* masuk ke `[domainanda.com/](https://domainanda.com/)*`, Nginx meneruskannya ke *container* Next.js (Frontend).
* Nginx juga bisa dikonfigurasi untuk langsung menyajikan *asset* gambar beresolusi tinggi (Splash Art) dari *folder* statis secara langsung untuk mengurangi beban Next.js.



Pendekatan *containerized* ini memastikan dependensi Node.js, versi PostgreSQL, dan Redis tidak berbenturan dengan layanan lain yang mungkin sudah berjalan di server Linux yang sama.

1. **Persiapkan Repositori Terpisah:**
Pisahkan repositori (atau folder monorepo) antara Frontend (Next.js) dan Backend (Node.js) agar proses *build* Docker nantinya lebih ringan dan fokus.


2. **Inisialisasi Backend & Redis:**
Mulai dengan membangun rute API Backend yang terhubung ke Redis terlebih dahulu. Pastikan alur *fetch* ke Mihomo API dan penyimpanan ke *cache* Redis berjalan normal melalui pengujian di Postman/Insomnia.


3. **Inisialisasi Frontend:**
Bangun pondasi Next.js dengan Tailwind dan hubungkan ke Backend lokal. Buat satu halaman *dummy* untuk menampilkan JSON dari Backend.


4. **Containerization:**
Buat `Dockerfile` untuk masing-masing Frontend dan Backend, lalu buat satu `docker-compose.yml` untuk merangkai Frontend, Backend, Redis, dan PostgreSQL dalam satu jaringan tertutup (*bridge network*).
