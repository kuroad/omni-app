Membedah tumpukan teknologi (Tech Stack) secara rinci sangat penting agar aplikasi Omni-App berjalan dengan tangguh, kebal dari *error* versi, dan optimal saat digunakan. Arsitektur terbaru ini (Omni-App 3.0) beralih ke ekosistem Python di bagian backend untuk stabilitas ORM dan performa konkuren yang sangat tinggi.

Berikut adalah rincian mendalam untuk Tumpukan Teknologi aplikasi web omni-ensiklopedia HSR:

### 1. Lapisan Frontend (Client-Side & UI)

Fokus di lapisan ini adalah kecepatan muat, SEO, dan interaktivitas tingkat premium (efek *Glassmorphism*).

* **Framework:** **Next.js (App Router) v14.2.15 dengan TypeScript**
  * **Kenapa:** Versi 14.2.x adalah versi paling stabil saat ini. Kita sengaja menghindari Next.js 15/16 karena terdapat perubahan drastis (di mana `params` menjadi *Promise* asinkron) yang sering menyebabkan gagal kompilasi (*build crash*). Versi ini mendukung *Server-Side Rendering* (SSR) yang krusial untuk SEO ensiklopedia tanpa mengorbankan stabilitas.

* **Data Fetching & State:** **TanStack Query (React Query)**
  * **Kenapa:** Sangat *powerful* untuk menangani data dinamis dari *showcase* UID. Mendukung fitur *stale-while-revalidate*, sehingga UI tidak akan *blank* saat memuat ulang UID.

* **Styling Engine:** **Tailwind CSS v3 + Shadcn UI**
  * **Kenapa:** Antarmuka HSR banyak menggunakan efek *glassmorphism* (kaca transparan) dan gradien. Tailwind efisien untuk meracik utilitas seperti `backdrop-blur-md` untuk meniru UI in-game.


### 2. Lapisan Backend (REST API Core)

Backend ini bertugas sebagai perantara pelindung (menahan *rate limit* Mihomo) dan penyedia data ensiklopedia murni.

* **Runtime & Framework:** **Python 3.11+ dengan FastAPI v0.110+**
  * **Kenapa:** Beralih dari Node.js (Fastify) ke Python (FastAPI). FastAPI sangat tangguh, memiliki validasi otomatis dengan Pydantic, dan sangat cepat secara asinkron. Selain itu, ekosistem pemrosesan data (ETL) di Python jauh lebih matang dibandingkan Node.js.

* **Mekanisme Rate Limiting Internal:**
  * Diimplementasikan di level FastAPI (menggunakan `fastapi-limiter` atau *middleware* kustom) untuk mencegah pengguna melakukan *spam* tombol "Refresh UID" yang bisa menghabiskan kuota *request* ke Mihomo.


### 3. Lapisan Manajemen Data (Database & ORM & Caching)

* **In-Memory Cache:** **Redis 7-alpine**
  * **Peran Krusial:** Saat pengguna mencari UID, FastAPI mengambil dari Mihomo, membalas ke pengguna, dan menyimpannya di Redis dengan *Time-To-Live* (TTL) 10 menit. Permintaan berikutnya akan dilayani oleh Redis dalam hitungan milidetik tanpa menyentuh API Mihomo sama sekali.

* **Relational Database:** **PostgreSQL 16-alpine**
  * **Peran:** Menyimpan sinkronisasi data statis ensiklopedia HSR (Karakter, Relik, Material).

* **Database ORM:** **Prisma Client Python (prisma-client-python)**
  * **Kenapa:** Sesuai instruksi, kita tetap mempertahankan ekosistem Prisma yang sudah kita kenal, namun menjalankannya dengan klien Python. Kita akan menyesuaikan versinya ke rilis stabil (misal: Prisma Client Python `0.12.x` dan mesin Prisma `5.x`/`6.x` yang matang) agar terhindar dari komplikasi *driver adapter* yang muncul di versi 7. Prisma Python sangat cocok dengan model *asinkron* dari FastAPI.


### 4. Lapisan Infrastruktur & Deployment

Semua servis akan dibungkus menggunakan **Docker** dan `docker-compose.yml`.

1. **Topologi Jaringan Internal Docker:**
   - Wadah `frontend` (Port 3000)
   - Wadah `backend` (Port 8000)
   - Wadah `postgres` (Port 5432)
   - Wadah `redis` (Port 6379)

2. **Strategi Proksi (Nginx / Next.js Rewrites):**
   - Nginx akan berada di lapis paling depan mendengarkan port 80/443.
   - Apabila permintaan klien menuju `/api/`, proksi akan melemparnya ke wadah `backend` (FastAPI).
   - Permintaan klien menuju halaman UI akan dilempar ke wadah `frontend` (Next.js).

Struktur ini memastikan isolasi penuh, di mana *crash* pada satu komponen tidak akan mematikan komponen lainnya, dan kode backend terpisah secara logis di ruang lingkup Python.
